# HUMAN_STYLE.md — короткие клиентские тексты без «ИИ-презентации»

Рабочий гайд для откликов и чатов Profi Agent. Для коротких сообщений
репетитора важнее не отдельные слова и знаки препинания, а **композиция и
конкретность оффера**.

## Что показали живые сообщения 04.09.2026

Проблема старых откликов была не в том, что они слишком грамотные. Они слишком
часто шли по одной схеме:

`приветствие → пересказ заявки → мини-методика → онлайн/60–90 минут → пробное → вопрос`

Даже когда слова меняются, такой каркас быстро считывается как генератор.
Противоположная крайность тоже не нужна: не надо вытаскивать редкие детали из
заказа, придумывать английские примеры или демонстрировать знание методик ради
ощущения «это написано именно вам».

Нужен простой конкретный оффер:

`могу помочь → предлагаю начать так → один следующий шаг`

Например:

> Здравствуйте! Могу помочь подтянуть разговорный английский. Предлагаю начать
> с пробного занятия: посмотрим текущий уровень и поймём, на чём лучше сделать
> упор. Когда вам удобно?

Для подготовки к экзамену:

> Добрый день! Могу помочь с подготовкой к ЕГЭ по информатике. Я бы начал с
> пробного занятия: посмотрим текущий уровень и определим, какие темы сейчас
> важнее всего подтянуть. Когда удобно попробовать?

Если клиент уже спрашивает цену:

> 60 минут — 2000 ₽, 90 минут — 3000 ₽. Для первого занятия я бы взяла
> 60 минут, чтобы спокойно посмотреть уровень. Какое время удобнее?

Сила таких сообщений не в «ошибках как у человека», а в том, что они
**функциональные**: есть понятное предложение и следующий шаг.

## A/B/C эксперимент `outreach_offer_v1`

Вместо бесконечной ручной правки одного промпта первый отклик теперь является
экспериментом с тремя фиксированными гипотезами.

- **A — direct offer:** прямо «могу помочь», простой первый шаг, один вопрос про время.
- **B — diagnostic:** «могу помочь», первое занятие как короткая диагностика уровня,
  затем один вопрос.
- **C — compact next step:** максимально короткий оффер, при необходимости один
  логистический факт, затем следующий шаг.

Вариант назначается кандидату **до первого LLM-вызова** и сохраняется в SQLite.
Выбор псевдослучайный, но стабильный по `experiment_id + order_id`: retry,
перезапуск процесса или fallback не перекидывают заказ из A в B/C. Это важно,
иначе эксперимент невозможно интерпретировать.

Внутри одного A/B/C-варианта композицию специально не рандомизируем. Менять
одновременно prompt и случайную структуру — добавлять шум в тест.

Когда захотим проверить другие гипотезы, не меняем смысл A/B/C задним числом,
а заводим новый `experiment_id`, например `outreach_offer_v2`.

## Что сохраняем для аналитики

`details_json.description` — исходное описание заказа с Профи, **не текст
модели**. Оно остаётся source data и не удаляется.

`triage_reason` / `llm_summary` — внутреннее объяснение `send/skip`. Оно полезно
для диагностики, но не является главным полем аналитики текста.

Для эксперимента в `candidates` сохраняются:

- `prompt_experiment`;
- `prompt_variant`;
- `prompt_assigned_at`;
- `first_reply_text` — первый реально подготовленный текст, не перезаписывается;
- `first_reply_source` — `llm` или `fallback`;
- `first_reply_at`;
- `first_client_reply_at` — когда агент впервые увидел ответ клиента.

Основная первая метрика:

`reply rate = клиенты, ответившие на отклик / подтверждённо отправленные LLM-отклики`

Fallback показывается отдельно и **не голосует за A/B/C**, потому что его текст
не был сгенерирован соответствующим prompt-вариантом.

Агрегация лежит во view `v_prompt_experiments`. Быстрый локальный отчёт:

```bash
uv run python scripts/ops/experiment_report.py
```

Для конкретной БД:

```bash
uv run python scripts/ops/experiment_report.py --db data/lang.db
```

Следующий уровень аналитики после накопления выборки — добавить outcomes
`trial_booked`, `trial_held`, `paid_student`. Reply rate — хороший ранний сигнал,
но конечная цель эксперимента всё равно конверсия в ученика.

## Правила первого отклика

1. Обычно 2–4 предложения, ориентир 160–320 символов. 500 — технический потолок.
2. В начале понятное предложение помощи: «могу помочь с...», «готов помочь с...»
   или естественный эквивалент.
3. Затем одна конкретная фраза о том, как предлагается начать.
4. Персонализация не обязательна. Обычно достаточно предмета или основной цели.
5. Не пересказывать клиенту его же заявку: «у вас intermediate», «Алексу 6 лет»,
   «задача понятна» не добавляют ценности.
6. Не объяснять всю методику в первом сообщении.
7. Не перечислять одновременно формат, длительность, методику, цель и пробное.
8. Один вопросительный знак максимум.
9. Не демонстрировать экспертность английскими фразами, названиями учебников,
   методик и buzzword-ами ради эффекта.
10. Не добавлять специально опечатки, ошибки или улыбки ради «человечности».

## Правила чата

Чат — не второй отклик. После ответа клиента не нужно снова продавать себя.

1. Сначала ответить на последний прямой вопрос.
2. Потом максимум одна короткая фраза про следующий шаг.
3. Цена, формат или время — факт в первой фразе, без вступления.
4. Обычно хватает 1–3 предложений и одного вопроса.
5. Не повторять методику из первого сообщения.

## Что особенно палит шаблон

- «задача понятна / задача ясна»;
- «поняла ваш приоритет»;
- «уровень X — хорошая база»;
- «значит уже есть база»;
- «самое время начать»;
- «поэтому на занятиях...»;
- «формат дистанционный»;
- `step by step`, «шаг за шагом», «закрываем пробелы»;
- два вопроса в конце;
- длинный гладкий абзац, где автор успел рассказать вообще всё;
- демонстративная персонализация по необычной детали заказа, которая не помогает
  договориться о следующем шаге.

Эти паттерны используются только как сигнал для **одной дополнительной попытки
перегенерации**, а не как бизнес-гейт. Retry обязан сохранить тот же A/B/C arm.

## Реализация

- `src/profi/copy_style.py` — общий стиль, versioned A/B/C prompts и style-check;
- `src/profi/llm/__init__.py` — максимум одна best-effort style retry;
- `src/profi/fastpath.py` — назначает и фиксирует variant до LLM;
- `src/profi/storage/store.py` — experiment fields, immutable first reply и views;
- `scripts/ops/experiment_report.py` — локальный A/B/C отчёт.

Контакты, ссылки, честность фактов и остальные safety-гейты по-прежнему
проверяются отдельным кодом. Style-check и A/B/C слой их не заменяют.
